# Дельта спецификации

## Purpose

Определяет, как входящие запросы к форвардящим эндпойнтам аутентифицируются статическим API-ключом, какие эндпойнты под это правило попадают, где оно неприменимо и что сервис делает при отказе.

## ADDED Requirements

### Requirement: Ключ защищает эндпойнты, которые маршрутизируют работу дальше
Сервис SHALL требовать заголовок `X-API-Key` на каждом эндпойнте, который перенаправляет запрос вызывающего дальше — во внешний сервис распознавания речи, во внешний сервис синтеза речи или во внешний языковой сервис. Ключ SHALL проверяться до того, как запрос будет перенаправлен, чтобы неаутентифицированный вызов не создавал нагрузки на внешний сервис.

#### Scenario: Форвардящий эндпойнт без заголовка
- **WHEN** клиент вызывает форвардящий эндпойнт без заголовка `X-API-Key`
- **THEN** сервис возвращает HTTP 401
- **AND** запрос не перенаправляется во внешний сервис

#### Scenario: Форвардящий эндпойнт с неверным ключом
- **WHEN** клиент вызывает форвардящий эндпойнт с заголовком `X-API-Key`, значение которого не совпадает с настроенным ключом
- **THEN** сервис возвращает HTTP 401
- **AND** запрос не перенаправляется во внешний сервис

#### Scenario: Форвардящий эндпойнт с верным ключом
- **WHEN** клиент вызывает форвардящий эндпойнт с настроенным API-ключом
- **THEN** запрос перенаправляется и обрабатывается

#### Scenario: Нефорвардящий эндпойнт без ключа
- **WHEN** клиент вызывает эндпойнт, отвечающий локально, без заголовка `X-API-Key`
- **THEN** сервис возвращает запрошенный ресурс

#### Scenario: Появился новый форвардящий эндпойнт
- **WHEN** добавляется эндпойнт, перенаправляющий запрос во внешний сервис
- **THEN** он защищён этим же правилом, и добавление эндпойнта не требует отдельного решения о защите

#### Scenario: Форвардящий эндпойнт распознавания речи
- **WHEN** клиент вызывает `POST /asr` без ключа
- **THEN** сервис возвращает HTTP 401

#### Scenario: Форвардящий эндпойнт синтеза речи
- **WHEN** клиент вызывает `POST /tts` без ключа
- **THEN** сервис возвращает HTTP 401

#### Scenario: Локально отвечающие эндпойнты
- **WHEN** клиент вызывает `GET /health`, `GET /ready`, `GET /`, `GET /questionnaire` или `GET /static/*` без ключа
- **THEN** сервис возвращает запрошенный ресурс

### Requirement: Браузерное демо не может предъявить ключ и остаётся открытым
Демонстрационная анкета, которую заполняет посетитель сайта в браузере, SHALL оставаться доступной без ключа: браузер не может хранить секрет, не выдавая его каждому посетителю, поэтому правило проверки ключа на этом эндпойнте SHALL NOT применяться. Это SHALL быть явным исключением из правила, а не его недосмотром.

#### Scenario: Посетитель отправляет анкету
- **WHEN** браузер посетителя отправляет анкету без заголовка `X-API-Key`
- **THEN** сервис принимает отправку и возвращает сгенерированный ответ

#### Scenario: Ключ был бы встроен в раздаваемый скрипт
- **WHEN** ключ для защиты браузерного демо был бы встроен в общедоступный скрипт
- **THEN** он был бы доступен любому посетителю и не защищал бы эндпойнт

### Requirement: API-ключ разбирается из конфигурации деплоя
Сервис SHALL разбирать входящий API-ключ из конфигурации, предоставленной окружением деплоя, включая имя, использовавшееся до перехода на Whisper, чтобы существующий деплой продолжал работать после обновления.

#### Scenario: Деплой поставляет секрет под прежним именем
- **WHEN** деплой поставляет API-ключ под прежним именем переменной окружения
- **THEN** сервис аутентифицирует запросы по этому ключу
- **AND** сервис не оставляет форвардящие эндпойнты незащищёнными

#### Scenario: API-ключ не настроен
- **WHEN** деплой не поставляет API-ключ ни под одним из поддерживаемых имён
- **THEN** сервис сообщает об отсутствующей конфигурации при старте
- **AND** сервис не допускает молчаливого неаутентифицированного доступа к форвардящим эндпойнтам

### Requirement: Входящий и исходящий ключи разбираются раздельно
Сервис SHALL разбирать входящий ключ клиента и исходящий ключ к вышестоящему сервису раздельно, из независимых источников, так чтобы оператор мог завести собственный входящий ключ, не выдавая своим клиентам ключ к вышестоящему сервису. Настройка только одного из них SHALL NOT приводить к тому, что оба значения совпадут.

#### Scenario: Оба ключа заданы раздельно
- **WHEN** оператор задаёт входящий ключ и исходящий ключ разными значениями
- **THEN** входящая проверка сверяется с входящим значением
- **AND** вышестоящему сервису предъявляется исходящее значение

#### Scenario: Задано только историческое имя
- **WHEN** оператор задаёт ключ только под именем, использовавшимся до перехода на Whisper
- **THEN** сервис работает, используя это значение для обеих ролей
- **AND** разведение ролей не требуется для сохранения работоспособности

#### Scenario: Разведение ролей выполнено
- **WHEN** оператор задаёт входящий ключ под именем, отведённым под входящую роль, и исходящий ключ под именем, отведённым под исходящую
- **THEN** клиент, предъявивший входящий ключ, проходит проверку
- **AND** ключ, предъявленный клиентом, не используется для обращения к вышестоящему сервису

### Requirement: Ключи генерируются оператором
Сервис SHALL позволять оператору задать собственное уникальное значение ключа, и инструкция по развёртыванию SHALL описывать, как это значение создаётся и куда помещается, так чтобы развёртывание не требовало значения, полученного извне.

#### Scenario: Оператор генерирует собственный ключ
- **WHEN** оператор создаёт случайное значение и помещает его в источник входящего ключа
- **THEN** сервис принимает это значение как входящий ключ
- **AND** клиент, предъявивший это значение, проходит проверку

#### Scenario: Значение по умолчанию отсутствует
- **WHEN** ни один источник ключа не задан
- **THEN** сервис не принимает никакого входящего ключа и не оставляет форвардящие эндпойнты открытыми
- **AND** инструкция по развёртыванию называет источник, который оператор должен заполнить

### Requirement: API-ключ не раскрывается
Сервис SHALL NOT включать настроенный API-ключ и никакие иные учётные данные в тело ответа, в сообщение об ошибке, в запись журнала или в раздаваемый браузеру контент.

#### Scenario: Аутентификация не пройдена
- **WHEN** запрос отклонён из-за неверного API-ключа
- **THEN** ни предъявленный, ни настроенный ключ не встречается в теле ответа

#### Scenario: Записывается ошибка
- **WHEN** сервис журналирует сбой, в котором участвовали учётные данные
- **THEN** запись журнала не содержит учётных данных

#### Scenario: Отдаётся браузерный контент
- **WHEN** сервис отдаёт скрипт или страницу браузеру
- **THEN** раздаваемый контент не содержит ключа
